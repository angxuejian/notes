# 优化 JavaScript：为了乐趣，也为了收益

> [原文地址](https://romgrk.com/posts/optimizing-javascript)，原文章中的示例并不会搬运过来，这里只作为翻译正文。

我经常觉得，很多 JavaScript 代码其实都比它本可以达到的速度慢得多，只是因为没有采用更合理的优化方式。下面总结的是一些我在实践中认为非常实用的优化技巧。

需要注意的是，性能和可读性往往需要权衡。至于什么时候应该优先追求性能，什么时候应该优先考虑可读性，就留给读者自己判断了。

另外还要说明一点，只要谈到性能优化，就绕不开基准测试。

如果这个函数本来只占整个程序运行时间的一小部分，那么花几个小时把它优化到快上 100 倍，也是没有意义的

如果要进行性能优化，第一步，也是最重要的一步，就是进行基准测试。关于这一点，我会在后面的章节中详细介绍。

也请注意，微基准测试通常都有一定的局限性，这一点也包括本文中的这些测试。我已经尽力避免常见问题，在采用文中的优化方法之前，请一定要先做好基准测试。

凡是能够提供可运行示例的场景，我都附上了对应的示例。这些示例默认展示的是我在自己的机器（Brave 122，Arch Linux）上运行得到的结果，不过你也可以亲自在自己的环境中运行它们。尽管我很讨厌这样说，Firefox 在性能优化方面稍显落后，不过 [目前](https://www.mozillafoundation.org/en/?form=donate-header) Firefox的访问量也是非常少，因此，我不建议把在 Firefox 上得到的测试结果作为判断性能的参考。
 
## 0. 避免不必要的工作

这听起来可能很明显，但仍然有必要把它放在这里，因为性能优化的第一步永远都是这一点：如果你想进行优化，首先应该思考能否减少需要执行的工作。这包括缓存计算结果、惰性计算以及增量计算等技术。具体采用哪种方式取决于实际场景。例如，在 React中，这通常意味着使用 `memo()`、`useMemo()` 以及其他适用的内置优化机制。

## 1. 避免字符串比较

> 关于基准测试
>
> 百分比的计算方式是：某项测试在 1 秒内完成的操作数 ÷ 表现最佳测试用例在 1 秒内完成的操作数。因此，表现最好的测试结果为 100%，其他结果则按比例计算；百分比越高越好。


正如你所见，两者之间的性能差距可能相当明显。这种差距未必来自 `strcmp` 逐字符比较字符串的开销，因为 JavaScript 引擎有时会使用字符串池，只需比较字符串引用即可，而无需逐字符比较。另一方面，这种差距还与 JS 引擎的内部表示有关：整数通常按值（passed by value）传递，而字符串始终以指针（passed as pointers）的形式传递；访问内存本身就是一项代价较高的操作（见第 5 节）。因此，在大量使用字符串的代码中，这种差异可能会带来非常显著的性能影响。

举个实际例子，我仅通过将字符串常量替换为数字，就让[ JSON5 javascript](https://github.com/json5/json5/pull/278) 解析器的运行速度提高了 2 倍*。

## 5. 避免缓存未命中

理解这一点需要一些底层知识，但它同样会影响 JavaScript 的性能，因此这里简单解释一下。从 CPU 的角度来看，从 RAM 中读取数据的代价很高。为了加快运行速度，CPU 主要依赖两种优化机制。

### 5.1 预取

第一种优化是预取（Prefetching）：CPU 会提前读取更多的数据，希望这些正是你接下来要访问的数据。它总是假设：如果你访问了某个内存地址，那么你很可能还会继续访问紧随其后的那片内存区域。因此，顺序访问数据至关重要。下面的示例展示了随机访问内存对性能造成的影响。

**What the eff，我该如何去做呢？**

这一点可能是最难真正应用到实践中的，因为 JavaScript 无法控制对象在内存中的布局。不过，你仍然可以利用这些知识来优化程序。例如，在重新排列或排序数据之前，先完成需要的操作。不要认为连续创建的对象在一段时间之后仍然会位于原来的内存位置，因为垃圾回收器可能会移动它们。不过也有一个例外，那就是数字数组，尤其是 TypedArray。

### 5.2 L1/L2/L3 缓存

第二种优化机制是CPU使用的 L1/L2/L3 缓存：它们就像速度更快的 RAM，但由于制造成本很高，因此容量也小得多。它们保存着来自主内存的一部分数据，工作方式类似于 LRU 缓存。当数据处于"热点"状态（即正在频繁访问）时，会进入缓存；当新的热点数据需要空间时，旧数据则会被写回主内存。因此，这里的关键是尽可能减小工作集（working dataset）的大小，让它始终能够放进高速缓存中。下面的示例展示了当工作集依次超出 L1、L2 和 L3 缓存容量时，对性能造成的影响。

来看一个真实的例子，我曾经遇到过这样一个情况：我们通过将数组替换为链表，就把一个[函数的运行时间从 5 秒降低到了 22 毫秒](https://github.com/mui/mui-x/pull/9200)。

## 11. 基准测试

我把这一部分放到最后，只有一个原因：我需要先通过前面那些有趣的章节建立起可信度。现在我（希望如此）已经建立起这种可信度了，那么让我告诉你：基准测试是优化中最重要的一部分。不仅如此，它也非常难。即使有 20 年的经验，我有时仍然会创建出有问题的基准测试，或者错误地使用性能分析工具。所以，无论你做什么，**请务必在正确进行基准测试上投入最多的精力**。

### 11.0 从占用时间最多的部分开始

你的首要任务应该始终是优化那个占据运行时间最大部分的函数或代码部分。如果你把时间花在优化其他地方，而不是最主要的部分上，那么你就是在浪费时间。

### 11.1 避免微基准测试

在生产模式下运行你的代码，并根据观察到的结果进行优化。JS 引擎非常复杂，在微基准测试中的表现往往与真实场景中的表现不同。例如，来看下面这个微基准测试：

```
# 代码示例 -> 请前往原文查看
```

如果你前面注意到了这一点，就会意识到，引擎会针对 `{ type: string, count: number }` 这种结构对函数进行特化。但是，在你的真实使用场景中，这一点还成立吗？`a` 和 `b` 是否始终都是这种结构，还是说你可能会接收到各种不同结构的对象？如果在生产环境中你会接收到很多不同的结构，那么这个函数的表现就会有所不同。

### 11.2 质疑你的结果

如果你刚刚优化了一个函数，结果它现在快了 100 倍，那就应该怀疑这个结果。尝试证明你的结果是错误的，在生产模式下试试，拿各种情况去测试它。同样，也要质疑你的工具。仅仅是使用 DevTools 观察一个基准测试，就可能改变它的行为。

### 11.3 选择你的目标

不同的引擎对某些代码模式的优化效果可能比其他引擎更好，也可能更差。你应该针对与你相关的引擎进行基准测试，并确定哪个引擎更重要，优先优化它。Babel 中就有[一个真实案例](https://github.com/babel/babel/pull/16357)：提升 V8（chorme）上的性能，却意味着 JSC（Safari） 的性能下降。

## 12. 性能分析与工具

一些关于性能分析和 DevTools 的补充说明。

### 12.1 浏览器中的常见坑

如果你是在浏览器中进行性能分析，请确保使用一个干净、没有额外配置的浏览器环境。我甚至会专门使用一个独立的浏览器来做这件事。如果你在进行性能分析时启用了浏览器扩展，它们可能会干扰你的测量结果。尤其是 React DevTools，它会显著影响测试结果，使渲染代码看起来比用户实际体验到的速度更慢。

### 12.2 基于采样的性能分析 vs 基于结构的性能分析

浏览器的性能分析工具属于基于采样的性能分析器，它们会以固定的时间间隔对你的调用栈进行采样。这种方式有一个很大的缺点：一些执行时间非常短但调用非常频繁的函数，可能恰好在这些采样点之间被调用，从而在你最终看到的调用栈图表中被严重低估。可以使用带有自定义采样间隔的 Firefox DevTools，或者使用 CPU 节流功能的 Chrome DevTools，来缓解这个问题。

### 12.3 常用的性能分析工具

除了常规的浏览器 DevTools 之外，你也可以了解一下下面这些内容：

- Chrome DevTools 有不少实验性功能，可以帮助你找出性能变慢的原因。Style Invalidation Tracker（样式失效跟踪器）在你需要排查浏览器中的样式/布局重新计算时非常有用。https\://github.com/iamakulov/devtools-perf-features

- deoptexplorer-vscode 扩展可以加载 V8/Chromium 的日志文件，帮助你了解代码什么时候触发了反优化，比如向函数传入不同的对象结构时。你不需要这个扩展来读取日志文件，但它能让整个体验舒服很多。https\://github.com/microsoft/deoptexplorer-vscode

- 你还可以为每个 JS 引擎编译它的 debug shell，以便更详细地了解它是如何工作的。这样你就可以运行 perf 和其他底层工具，还可以查看每个引擎生成的字节码和机器码。[V8](https://mrale.ph/blog/2018/02/03/maybe-you-dont-need-rust-to-speed-up-your-js.html#getting-the-code)、[JSC](https://zon8.re/posts/jsc-internals-part1-tracing-js-source-to-bytecode/)、SpiderMonkey（链接未找到）
